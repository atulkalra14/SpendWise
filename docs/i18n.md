# Internationalization (i18n)

Single source of truth for languages and the translation process. Keep it short and current.

## Languages

| Language | Code | Status                         | Notes                                      |
| -------- | ---- | ------------------------------ | ------------------------------------------ |
| English  | `en` | Default and fallback           | All new keys are written in English first. |
| German   | `de` | Second language, supported now | Required by `npm run i18n:check`.          |
| Others   | –    | Added later by developers      | Follow "Adding a language" below.          |

Open decisions (record the answer as an ADR in `docs/adr/`):

- [ ] German tone: formal (Sie) or informal (du)?
- [ ] Who translates and reviews German texts (internal, agency, customer)?
- [ ] Will right-to-left languages (Arabic, Hebrew) ever be needed? If yes, plan UI testing early.

## Where texts live

| What                                              | Where                                                                      | Example                                      |
| ------------------------------------------------- | -------------------------------------------------------------------------- | -------------------------------------------- |
| Model and annotation labels                       | `_i18n/i18n.properties` (English fallback), `_i18n/i18n_<lang>.properties` | `@title: '{i18n>Title}'`                     |
| Runtime messages (errors, warnings, info)         | `_i18n/messages.properties`, `_i18n/messages_<lang>.properties`            | `req.reject(400, 'ERR_X', 'field', [value])` |
| Translatable business data (code lists, statuses) | CDS `localized` elements, seed in `db/data/<Entity>_texts.csv`             | status names per language                    |
| Fiori app texts                                   | `app/<app>/webapp/i18n/i18n.properties` and `i18n_<lang>.properties`       | UI5 resource bundle                          |

Rules:

- No hard-coded user-facing text in handlers, CDS, annotations or UI code.
- Use placeholders filled from `args` (`req.reject(409, 'ORDER_EXCEEDS_STOCK', 'quantity', [stock, quantity])`), never concatenate translated fragments. The exact placeholder syntax (`{0}` or named) is confirmed at project setup; `scripts/check-i18n.js` accepts both.
- Keys are stable and descriptive. Never reuse a key for a different meaning. Runtime message keys are `UPPER_SNAKE_CASE` and start with the context (`ORDER_EXCEEDS_STOCK`); label keys are `PascalCase` (`OrderDate`).
- The language comes from the request (`Accept-Language` or `sap-language`). Read it with `req.locale`.
- Never hard-code date, number or currency formats.
- Do not delete a key that translations or released apps still use without a deprecation note.
- Fiori apps: one UI5 resource bundle per app at `app/<app>/webapp/i18n/`; set `supportedLocales` and `fallbackLocale` in `manifest.json`.
- Keep the `cds.i18n` defaults (default language `en`, folders `_i18n` and `i18n`). Capire warns that changing them also affects the bundles of reuse packages and the framework itself. Verify any `cds.i18n` option against capire before using it.
- Plan for right-to-left languages (for example `ar`, `he`) in UI work; test at least one RTL language if any is supported.
- German text is about 30% longer than English. Check layouts with long texts.

## Writing a new text (every feature)

1. Add the key and the English text to the default file (`i18n.properties` or `messages.properties`).
2. Add the German text to the matching `_de` file in the same change.
3. Run `npm run i18n:check`. It must have no errors.
4. If Claude drafted the German text, list the keys in the PR description under "German texts need native review".

Claude may draft German texts so the check passes. A draft is not a reviewed translation: a native speaker approves it before release.

## Adding a language later (example: French, `fr`)

No code change should be needed. If one is, treat that as a design bug and fix the design.

1. Record the decision as an ADR (who translates, tone, RTL or not).
2. Add `fr` files next to every existing bundle: `_i18n/i18n_fr.properties`, `_i18n/messages_fr.properties`, `app/<app>/webapp/i18n/i18n_fr.properties`.
3. Add translations for all `localized` data: rows for `fr` in each `db/data/*_texts.csv`.
4. Add `fr` to `supportedLocales` in each app's `manifest.json`.
5. Add `fr` to the language list of the check: in `package.json` change `--languages=en,de` to `--languages=en,de,fr`.
6. Update the language table above and the "Supported languages" line in `CLAUDE.md`.
7. Add a French case to `test/i18n/`.
8. Have a native speaker review the texts. Check layout and fonts. If the language is right-to-left, test the UI in RTL mode.

## Checking

Add this script to `package.json`:

```json
"scripts": {
  "i18n:check": "node scripts/check-i18n.js --languages=en,de"
}
```

`scripts/check-i18n.js` has no dependencies. It scans every `_i18n/` and `i18n/` folder.

| Result           | Condition                                                                                                                |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------ |
| Error (fails CI) | missing language file, key missing in a language, empty value, placeholder mismatch, duplicate key, missing default file |
| Warning          | key not in the default file, language file not in `--languages`, key not found in sources (may be used dynamically)      |

Options: `--languages=en,de`, `--default=en`, `--root=<dir>`, `--fail-on-unused` (treat unused keys as errors). The language list can also come from the `I18N_LANGUAGES` environment variable.

## Tests

`test/i18n/` covers:

- A request with `Accept-Language: de` returns the German message and German `localized` data.
- A request in a language without a translation falls back to English.
- Message placeholders are filled in both languages.

## Glossary

Agree on fixed German terms for domain words so the whole app uses the same word.

These terms are used in the current bundles (draft, pending native review). Formal address ("Sie") is used throughout.

| English          | German                | Note                                               |
| ---------------- | --------------------- | -------------------------------------------------- |
| Expense          | Ausgabe               | Plural "Ausgaben"                                  |
| Income           | Einnahmen             | Always plural                                      |
| Savings / Saved  | Ersparnisse / Gespart | "Gespart" is the label on the landing page card    |
| Budget           | Budget                | Plural "Budgets"                                   |
| Transaction      | Transaktion           | Plural "Transaktionen"                             |
| Category         | Kategorie             | Subcategory: "Unterkategorie"                      |
| Settings         | Einstellungen         | Navigation item only                               |
| Preferences      | Voreinstellungen      | Profile tab and panel; never "Einstellungen" there |
| Profile          | Profil                |                                                    |
| Display name     | Anzeigename           |                                                    |
| Password         | Passwort              |                                                    |
| Terms of Service | Nutzungsbedingungen   | Legal texts are not translated yet                 |
| Privacy Policy   | Datenschutzerklärung  | Legal texts are not translated yet                 |

## Multitenancy

Tenant-specific text overrides are not supported unless an ADR decides otherwise.
